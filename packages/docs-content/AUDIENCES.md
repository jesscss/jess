# Docs architecture: one pool, two facings

Jess and Less docs are built from **one content pool** and deployed as **two audience "facings"**:

- **Jess-facing** site (`packages/docs`) — build-time audience `jess` (e.g. `jesscss.dev`)
- **Less-facing** site (`packages/docs-less`) — build-time audience `less` (e.g. `lesscss.org`)

There is **no per-site content copy** and **no sync step to keep in step** — a doc lives once, declares who it is `for`, and each facing renders the docs (and the per-audience framing) that belong to it. This structurally prevents the stale-mirror problem (the old `packages/docs/docs` mirror) from ever recurring.

## The pieces

### 1. `audiences` frontmatter is the source of truth
Every doc declares its audiences. A doc appears on a facing **iff** its `audiences` includes that facing.

```mdx
---
title: Less 4.x → 5.x breaking changes
audiences: [jess, less]     # shows on BOTH facings
origin: shared
---
```

```mdx
---
title: Sass (SCSS) compatibility
audiences: [jess]           # Jess-facing only
origin: jess
---
```

### 2. Materialized per-facing trees (never committed)
A prebuild step in `@jesscss/docs-content` composes one tree per facing by filtering the pool on `audiences`:

```
docs-content/docs/**                     ← single authored pool (jess/, less/, shared/)
docs-content/.site/jess/**   (generated) ← every doc whose audiences ⊇ {jess}
docs-content/.site/less/**   (generated) ← every doc whose audiences ⊇ {less}
```

`.site/` is `.gitignore`d (root `.gitignore`: `packages/docs-content/.site/`) and regenerated on every `dev`/`build`, so it is never a mirror to maintain. Each site's Docusaurus `path` points at its `.site/<audience>` tree, so **the sidebar is automatically correct per facing** — no runtime filtering needed for cross-facing visibility.

Script: `packages/docs-content/scripts/build-facings.mjs`, run as `pnpm --filter @jesscss/docs-content build:facings`. Each site wires it as a `predev` + `prebuild` hook (npm lifecycle) so `docusaurus start`/`build` always sees fresh trees.

**Path mapping** (`build-facings.mjs`):
- A doc under `docs/<pool>/…` (`pool` ∈ `jess|less|shared`) maps to `.site/<facing>/…` by stripping the leading pool segment. Numeric prefixes (`01-…`) are preserved so the autogenerated Jess sidebar keeps its order.
- A doc may override its per-facing location with a `facing_paths: { jess: <relpath-no-ext>, less: <relpath-no-ext> }` frontmatter map. When present, the file lands at `.site/<facing>/<facing_paths[facing]>.<ext>`.
- Non-doc assets (`_category_.json`, images): files under `jess/`/`less/` copy only to that same facing; files under `shared/` copy to every facing.

### 3. Build-time audience → per-audience *framing*
Each site sets one custom field:

```ts
// packages/docs/docusaurus.config.ts        (Jess-facing)
customFields: { siteAudience: 'jess' }
// packages/docs-less/docusaurus.config.ts   (Less-facing)
customFields: { siteAudience: 'less' }
```

`AudienceProvider` (in the shared theme) reads `siteConfig.customFields.siteAudience` via `useDocusaurusContext` and uses it as the initial audience, so a **shared** doc renders the wording that is true for the reader. This is the "say what *Less* does, not what *Jess* does" guarantee. The in-site toggle can still override the audience for preview (persisted to `localStorage`), but the built default is the site's own facing.

`<AudienceGate>` takes `include?: Audience[]` / `exclude?: Audience[]` (`Audience = 'less' | 'jess' | 'sass'`) and renders its children only when the current audience matches. It is registered globally through swizzled `MDXComponents`, so `<AudienceGate>` works in any `.mdx` doc.

### The shared audience theme

The audience theme components (`AudienceContext`/`AudienceProvider`, `AudienceGate`, `AudienceToggle`, swizzled `Root`, `MDXComponents`, `NavbarItem`) live in **both** `packages/docs/src/theme` and `packages/docs-less/src/theme` as identical copies.

> **Decision:** a shared `@jesscss/docs-theme` package (a Docusaurus plugin exposing `getThemePath`) was attempted first, but contributing the theme as a *plugin* layer broke `@theme-original/*` resolution site-wide (recursive `NavbarItem`/`MDXComponents`, blank pages on every route including blog/404). Copying the components into each site's own `src/theme` is the proven Docusaurus swizzle layout and both sites build cleanly with it. The duplication is a handful of small presentational files; if a shared package becomes worthwhile later, it should ship **compiled** theme JS, not a `getThemePath` at TS source.

Because `.site/<audience>` already contains only that audience's docs, the sidebar is correct per facing at build time. The old `DocSidebarItems` swizzle that tried to filter the sidebar at runtime (and only ever stubbed `getDocAudiences`) was **removed** — it is no longer needed and must not lie about audiences.

## Real example: the shared Less 4→5 page

One file, two facings, audience-correct framing. This is the real page at `docs/shared/less-v5-breaking-changes.mdx`:

```mdx
---
title: Less 4.x → 5.x breaking changes
audiences:
  - jess
  - less
origin: shared
slug: /migrating/less-v5-breaking-changes
facing_paths:
  jess: 01-getting-started/07-less-v5-breaking-changes
  less: usage/less-v5-breaking-changes
---
import AudienceGate from '@theme/AudienceGate';

<AudienceGate include={['less']}>

Migrating a **Less 4.x** project to **Less 5.x**. Less 5.x runs on the Jess engine,
so behavior tracks CSS more closely while keeping Less semantics.

</AudienceGate>

<AudienceGate include={['jess']}>

Coming to **Jess** from **Less 4.x**? Jess *is* the engine behind Less 5.x, so the same
breaking changes apply.

</AudienceGate>

## Removed: inline backtick JavaScript

`` `...` `` inline JS is removed (a parse error, not opt-in). Migrate to `@plugin` / `@-use`.

## Imports: `@import` → `@-import`

<AudienceGate include={['less']}>`@import "foo";` still resolves but warns; prefer explicit file-relative paths.</AudienceGate>
<AudienceGate include={['jess']}>Use `@-import "./foo.less";` — Jess requires file-relative imports to be explicit.</AudienceGate>

## …the rest of the breaking-changes list (shared body)
```

- On **lesscss.org** the reader sees the Less intro and `@import` framing.
- On the **Jess** site the same page shows the Jess intro and `@-import` framing.
- The breaking-changes *facts* are written once.

`facing_paths` places the one file under the Jess "Getting Started" area (`01-getting-started/07-…`, autogenerated sidebar) and the Less "Usage" area (`usage/less-v5-breaking-changes`, added manually to `sidebars/less.js` next to *Migrating to v5*).

> **Less site note:** the Less facing sets `markdown.format: 'detect'` (was `'md'`). Existing Less docs are CommonMark `.md` and stay that way; the shared page is `.mdx` and needs real MDX so JSX props like `include={['less']}` evaluate. Under the old global `'md'` format those props were dropped and every gate rendered unconditionally.

## Semantics test (what a "Less" reader sees)
Because the Less facing is built with `siteAudience: 'less'`:
- Only `audiences ⊇ {less}` docs are in its sidebar (no Jess-only pages leak in).
- Every `<AudienceGate include={['jess']}>` block is omitted; `include={['less']}` blocks render.
- Prose reads as "what Less does."

## Migration path (incremental, non-breaking)
1. Land the materialization script + `.site/` gitignore + build-time `siteAudience` on both sites; point each `path` at `.site/<audience>`. Existing `docs/jess` (tagged `[jess]`) and `docs/less` (tagged `[less]`) flow through unchanged.
2. Move genuinely-cross-audience pages into `docs/shared/**` tagged `[jess, less]` (starting with the Less 4→5 page).
3. Wire `<AudienceGate>` to read `siteConfig.customFields.siteAudience` as its default.
4. Over time, collapse duplicated jess/less pages into shared audience-gated ones.

## Versioning policy

**Do not use Docusaurus `versioned_docs`.** Less and Jess version on *independent* axes (Less 5
while Jess 2), and tree-versioning assumes a single axis — snapshotting a shared page into both a
"Less 6" and a "Jess 2" tree has no clean answer. We sidestep it entirely: the docs are **not**
organized by version.

- **The pool is always "current/next"** — one living source, accurate for every facing *now* via
  `<AudienceGate>`. Two version axes never collide here because nothing is frozen here.
- **Deltas within a major live in content** — migration guides + inline "changed in 5.x"
  admonitions (a `<Since v="5.2">`-style gate is fine). Language docs are ~95% version-invariant
  (a variable's syntax doesn't change between Less 5 and 6), so full tree-versioning is
  disproportionate.
- **A MAJOR release freezes only that facing into a static archive** (e.g. `lesscss.org/v4/`),
  linked from the migration guide — taken at that tool's own cadence, independent of the other
  facing. Not a live-maintained Docusaurus version; a frozen snapshot.

Asymmetry this handles cleanly: **Less** has a large legacy userbase and *does* archive at majors;
**Jess** is new, has no old-version readers yet, and stays rolling with in-content "since" notes.
Per-facing independence lets Less archive while Jess rolls, neither forcing the other.
