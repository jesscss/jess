This doc explains how Jess parses and compiles **SCSS** (Sass’s CSS-like syntax), and how Sass-only constructs are mapped into Jess’s AST and (when possible) into Jess-native semantics.

Jess’s goal is to make **Sass input parseable**, while preferring **Jess-native output semantics** where they’re strictly better (for example, maps).

## What SCSS adds beyond CSS

Sass extends CSS with (at least) the following features:

- **Variables**: `$var: value;` ([Sass variables](https://sass-lang.com/documentation/variables/))
- **Interpolation**: `#{...}` in selectors, property names, and values ([Interpolation](https://sass-lang.com/documentation/interpolation/))
- **Mixins/includes/content blocks**: `@mixin`, `@include`, `@content`, `using (...)` ([Mixins](https://sass-lang.com/documentation/at-rules/mixin/))
- **Control directives**: `@if`, `@for`, `@each`, `@while`, `@error`, `@warn`, `@debug` ([Control directives](https://sass-lang.com/documentation/at-rules/control/))
- **Module system**: `@use`, `@forward`, configuration via `with (...)` ([use](https://sass-lang.com/documentation/at-rules/use/), [forward](https://sass-lang.com/documentation/at-rules/forward/))
- **Maps and lists**: including built-in helpers like `map.get()` ([Maps](https://sass-lang.com/documentation/values/maps/), [sass:map](https://sass-lang.com/documentation/modules/map/))
- **Extend + placeholders**: `@extend` and `%placeholders` ([extend](https://sass-lang.com/documentation/at-rules/extend/), [placeholders](https://sass-lang.com/documentation/style-rules/placeholder-selectors/))
- **@at-root**: explicit control over nesting output ([at-root](https://sass-lang.com/documentation/at-rules/at-root/))
- **Nested declarations** (“property nesting”) ([declarations](https://sass-lang.com/documentation/style-rules/declarations/))

## At-rule mapping: Sass → Jess

Jess keeps compiler-level at-rules prefixed with `-` to avoid collisions with the evolving CSS standard library.

### `@use` (stylesheets) → `@-compose`

Sass:

```scss
@use './theme' as theme;
.box { color: theme.$primary-color; }
```

Jess equivalent:

```scss
@-compose './theme' as theme;
.box { color: $theme.primary-color; }
```

Jess’s module import node is `StyleImport` (see `packages/core/src/tree/import-style.ts`). It supports namespaces, configuration, and export/protection flags.

### `@use` (scripts) → `@-use` / `@-from` (by extension)

In Jess, `@-use` and `@-from` are for importing JS/TS/JSON modules (see `packages/core/src/tree/import-js.ts`).

When parsing SCSS, Jess will treat `@use` as a stylesheet import by default, but if the `@use` path clearly targets a script module (for example `./tokens.js`, `./tokens.ts`, `./tokens.json`), it will parse to a JS import node instead.

### `@forward` (SCSS) → `@-compose (forward)`

Jess models Sass’s forwarding semantics using `@-compose` flags as described in [At-rules](/docs/language/atrules).

## Sass maps → Jess collections

Sass maps are syntactically awkward compared to CSS rules. Jess maps them into the `Collection` node, which is a “map-like Rules” structure.

Sass:

```scss
$font-weights: ("regular": 400, "medium": 500, "bold": 700);
```

Jess AST shape (conceptual):

```scss
$font-weights: {
  regular: 400;
  medium: 500;
  bold: 700;
}
```

### Key normalization rules

- **Quoted string keys** with no interpolation are treated as plain keys.
  - `"regular"` becomes `regular` (no quotes) in the corresponding `Declaration` name.
- More complex Sass map keys (colors, lists, etc.) are supported by Jess collections, but the SCSS mapping rules depend on how the key can be represented as a stable collection key (see [Namespaces, collections, and maps](/docs/language/namespaces-and-maps)).

## `map-get()` and `map.get()` → Reference lookups

Sass commonly accesses map keys via:

```scss
@use "sass:map";

.box {
  font-weight: map.get($font-weights, "medium");
}
```

Jess does **not** treat this as a normal function call. Instead, the SCSS parser desugars:

- `map-get($map, $key[, ...])`
- `map.get($map, $key[, ...])`

into a **Reference lookup chain**:

- Evaluate the map expression (often `$font-weights`)
- Look up the key(s) as nested property/index accesses

This is the same core mechanism Jess uses for `$theme.colors.primary` and array/map-like access.

## Placeholder selectors (`%foo`)

Sass placeholder selectors don’t emit CSS unless they’re extended.

Jess parses:

- `%foo` as selector name `\foo`

This name conversion makes placeholders syntactically distinguishable from normal selectors while still being a selector-like key in the registry.

### Placeholder visibility (deferred implementation)

Sass placeholders are “silent” until extended. Jess will eventually model this by marking placeholder-origin rulesets as non-visible until extended. This likely requires special-casing in extend behavior and/or ruleset visibility rules, and is intentionally deferred while extend behavior is being stabilized.

### Cross-module behavior

Sass’s module system allows extending placeholders across module boundaries, with private placeholders (leading `_` or `-`) restricted to their defining module (see Sass’s placeholder docs above). Jess will align with this behavior, and we expect placeholders to behave as an “extendable API” across composed modules (details tracked as deferred work).

## Variable flags: `!global` and `!default`

Sass supports `!global` and `!default` on variable assignments ([variables](https://sass-lang.com/documentation/variables/)).

Jess’s SCSS support intentionally does **not** implement Sass’s full `!global` shadowing model. Instead, SCSS `!global` will be treated as “set existing / do not shadow” (Jess’s `setDefined` behavior), which is equivalent to `!global` *unless the user has already shadowed the variable in a narrower scope*—in that case, the user must refactor the source for clarity.

`!default` exists in Sass primarily to support module configuration (`@use ... with (...)`). Jess will align with Sass’s `@use` configuration behavior by ensuring configurable variables are explicitly marked and handled accordingly.
