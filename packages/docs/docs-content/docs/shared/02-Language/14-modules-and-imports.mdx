Every preprocessor lets you split styles across files and pull them back
together. The **concept** is the same everywhere — the **spelling** and the
**scoping rules** are what differ.

<AudienceGate include={['less']}>

# Imports in Less

In Less you compose stylesheets with `@import`. Less doesn't care where you put
an `@import` — it can appear after other rules — and it resolves the file
relative to the current one.

```less
.foo { background: #900; }
@import "./this-is-valid.less";
```

## File extensions

`@import` behaves differently depending on the extension:

- `.css` → treated as CSS; the `@import` is left in the output as-is.
- any other extension → treated as Less and inlined.
- no extension → `.less` is appended and the file is imported as Less.

```less
@import "./foo";      // ./foo.less is imported
@import "./foo.less"; // ./foo.less is imported
@import "./foo.css";  // left in place, as-is
```

Prefer a leading `./` for local files. Less also accepts bare specifiers
(`@import "my-module";`), which often resolve package/module imports, so the
explicit `./` signals local-file intent.

## Import options

Less extends CSS `@import` with options: `@import (keyword) "file";`

| Option | Effect |
| --- | --- |
| `reference` | Load the file but output nothing unless referenced (via mixin or `:extend`). |
| `inline` | Include the source verbatim without processing it. |
| `less` / `css` | Force the file to be treated as Less or CSS regardless of extension. |
| `once` (default) / `multiple` | Import a file once, or allow repeats. |
| `optional` | Don't error if the file is missing. |

You can combine keywords: `@import (optional, reference) "foo.less";`

## Moving to modules (`@compose`)

`@import` folds another stylesheet in with the old **leaky scope**, and it's
*heuristic* — the extension and options decide whether it passes through as CSS or
inlines as source. Its explicit form, `@-import`, always folds as source (no
guessing). Both are **discouraged in Less 5.x** and warn: the fix for either is
the module system, **`@compose`** — a namespaced import with isolated scope and
per-import configuration.

You can write the module rule bare or dashed — `@compose` and `@-compose` are the
same rule; the dash is the collision-safe canonical, but the bare form is a fully
supported convenience. Your existing `@import` keeps working (with a warning), so
migrate at your own pace.

```less
// Discouraged — the leaky source-fold (both warn):
@import "theme";         // heuristic (CSS-or-source)
@-import "./theme.less"; // explicit source-fold

// The module system — use this:
@compose "./theme.less" as theme;

.box { color: @theme[primary-color]; }
```

:::note
The exact verbosity of the `@import` / `@-import` "use `@compose`" warning is still
being finalized; the direction — `@compose` as the module system — is settled.
:::

</AudienceGate>

# From `@use`/`@forward` to `@-compose`

Modern Sass replaced global `@import` with a real module system: `@use` loads a
file under a namespace with isolated scope, and `@forward` re-exports another
module's API. Jess keeps that model — it just spells the at-rules with a leading
dash so they never collide with the evolving CSS standard library.

| Sass | Jess | Notes |
| --- | --- | --- |
| `@use "./theme";` | `@-compose "./theme";` | Namespaced, isolated-scope import. |
| `@use "./theme" as t;` | `@-compose "./theme" as t;` | Explicit namespace. |
| `@use "./theme" with (…);` | `@-compose "./theme" with { … }` | Per-import configuration. |
| `@forward "./theme";` | `@-export "./theme";` | Forward a module's API downstream. |
| `@use "sass:math";` | `@-use '#sass/math';` | Built-in modules. |

```scss
// Sass
@use './theme' as theme;
.box { color: theme.$primary-color; }
```

```scss
// Jess
@-compose './theme' as theme;
.box { color: $theme.primary-color; }
```

`@forward "…" show/hide/as …` filtering is intentionally **not** evaluated —
visibility is a module's own concern. See
[Unsupported Sass+ features](/docs/guides/coming-from-sass/unsupported-sass-features).

</AudienceGate>

# Modules in Jess

Jess's module system is `@-compose`. It imports another stylesheet under a
namespace, evaluates it in **isolated scope**, and lets you configure it per
import. Compiler at-rules are dash-prefixed so they never clash with future CSS.

```less
@-compose './theme' as theme;

.box {
  color: $theme.primary-color;
}
```

- **Namespace** is inferred from the file name, or set with `as name` (use
  `as *` to compose without a namespace — discouraged, since it's harder to
  trace where values come from). Namespaced `$extend` targets are covered in
  the Jess [at-rule reference](/docs/Language/atrules#extend); a namespace is
  an optional filter, not a required path.
- **`with { … }`** provides configuration for this compose only. It overrides
  the module's defaults without changing how another compose of that module
  begins.
- **`set { … }`** establishes a one-time, compilation-wide configuration for
  the resolved module. Later composes of that same module reuse those values.
- **`@-compose (reference)`** imports values/mixins without rendering rules
  (until extended); compositions are protected from downstream extension by
  default; **`@-compose (mutable)`** opts into downstream extension; **`(export)`**
  re-exports what it imports.
- **`@-export './x';`** forwards a module's API to consumers (Sass `@forward`).

See the full [at-rule reference](/docs/Language/atrules) for every flag.

## Scripts and data: `@-use` / `@-from`

Use `@-use` (Sass-module style) or `@-from` (ESM style) to pull values from
JavaScript, TypeScript, or JSON — and to load Jess's built-in `#less/*` and
`#sass/*` modules.

```scss
@-use './my-module.js';                       // namespace inferred
@-from './my-module.js' import (myFunc);      // named import

.box {
  width: $my-module.width;
  value: myFunc();
}
```

Values are read with a `$`-prefixed reference; imported **functions** are called
by their bare name (there is no `$myFunc()` call form).

JSON is a pure data import; evaluating local/package JS/TS while compiling needs
`@jesscss/plugin-js` (which isolates execution on Deno).

:::caution Resolution is not wired yet

In the 2.x alpha the module at-rules parse and round-trip to the output, but no
resolver exists: nothing is loaded, inlined, or evaluated, and referencing an
imported name raises `Name not found`. The syntax on this page is settled; the
loading behavior is the target.

:::

## `@-import` is a legacy bridge (discouraged)

Jess also supports `@-import` — the direct analog of Less/Sass `@import` — but it
emits a **deprecation warning**. It re-exports everything from the imported file
and changes the evaluation context on every call, which makes sources hard to
reason about. Reach for `@-compose` instead; keep `@-import` only for mechanical
migration.

```less
@-import './my-file.jess'; // works, but warns — prefer @-compose
```

</AudienceGate>

## Plain CSS `@import` still passes through

A native CSS `@import` — one that targets a URL or a `.css` file — is **not** a
source include. It is emitted verbatim so the browser fetches it at runtime.

```css
@import url("https://fonts.example/css?family=Inter");
@import "reset.css";
```

<AudienceGate include={['jess']}>

`.jess` has **no import heuristic**. A bare `@import` is *always* a plain CSS
at-rule — `@import "foo"`, `@import "foo.less"`, and `@import "foo.css"` all pass
straight through to the output. Folding a stylesheet in and evaluating it at
compile time is done **only** by an explicit, dash-prefixed compiler at-rule:

- **`@-compose`** — the module system (isolated scope, namespaced). Prefer this.
- **`@-import`** — always folds and evaluates the file in place (the leaky legacy
  shape; warns — reach for `@-compose`).

The dash is required. Bare `@use`, `@compose`, `@forward` are **not** valid Jess
at-rules — only `@-use`, `@-compose`, `@-export` are. That's the whole point of
the dash: `@import` stays pure CSS, and anything that touches the compiler is
unambiguously marked.

</AudienceGate>
