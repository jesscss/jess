jess grammar railroad diagrams

One page per dialect. Each is a standalone HTML file — the diagram library and its CSS are inlined, so nothing is fetched when you open it. The numbers behind these pages are on the complexity page.

The diagrams are generated by parseman/spec from the same rules() grammar that parses, by walking its combinator tree. They cannot drift from what actually parses. Regenerate with node scripts/generate-railroad-diagrams.mjs.

  • Less — 278 productions, entry rule Stylesheet

The rendering is deliberately not optimised

These pages are an instrument. A rule that renders as an unreadable ladder is telling you something about the rule, so nothing here smooths, collapses, re-wraps or prettifies a diagram to make it fit. Every rule the grammar defines is emitted — no reachability pruning — trivia rules included, in declaration order, and a monster is left looking like a monster.

The one rendering option in use is readable names for common terminals (IDENT rather than a 200-character character class). That changes how faithfully you can read the shape, not what the shape is. The balanced() pins below are the single exception, and they are forced: without them the emitter does not produce a page at all.

How to read a page

Productions are in declaration order; the entry rule for every dialect is Stylesheet (see each package's src/parse-with.ts). A box is a terminal or a reference to another rule; a reference is a link, so a rule whose diagram spells a construct out instead of linking to it has inlined that construct.

Known limitation: balanced()

buildSpecModel cuts reference cycles only at NAMED rules. balanced(open, close) deliberately keeps its own identity — its interior holds a self-reference — and that reference carries no rule name, so the walker recurses until the stack dies. Every rule listed above as pinned is a rule that directly contains a balanced(); pinning it to a prose terminal is the only lever the emitter offers. For CSS and SCSS the pinned rule is a delimiter scan, so nothing is lost. For the two Less rules it costs real structure: they are segment lists (whitespace / comma / group / quoted / text) and the page now shows only the summary.

Known limitation: word() and keywords()

word('@import') lowers to a single-alternative choice, and neither the spec model nor the renderer collapses it — so a lone @import is drawn inside an alternation frame, and the EBNF shows ("@import"). That is the emitter presenting a combinator below the abstraction it was authored at. It is a parseman issue, not a grammar one, and it does not inflate the counts on the complexity page: a one-arm choice adds no box, no row and no path.

Terminals

Common CSS-family patterns are given readable names (IDENT, NUMBER, WHITESPACE or COMMENT, …). Anything not on that curated list keeps its literal regex source: a spec that shows a pattern which is not the pattern would be worse than an ugly one. The remaining raw patterns are what makes a handful of diagrams wide; each diagram scrolls inside its own box, so the page itself never scrolls sideways.
