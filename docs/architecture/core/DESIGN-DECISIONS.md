# Design Decisions — canonical owner decision ledger

This is the **flat, greppable canonical ledger** for owner semantic and
architecture decisions. It holds both SETTLED rulings and OPEN owner questions,
so agents do not re-litigate settled work or silently implement an unanswered
proposal. One row per decision: the ruling/proposal + a pointer to its detail
doc and/or owner-memory note.

Rules of the road:

- **A row here is the ruling.** If code, a test, or a `.css` test-data file
  disagrees with a SETTLED row, the code/test/data is what changes — not the
  ruling. Confirm against the linked detail before acting.
- **OPEN rows are explicitly not settled** — they record the current state of a
  live thread so nobody mistakes silence for a decision.
- **"Source" pointers** are relative paths inside this dir unless prefixed
  `memory:` (a note in the owner's project memory,
  `.claude/projects/-Users-matthew-git-oss-jess/memory/<name>.md`).

## Ledger process (PROPOSED)

Every owner question that can alter parser facts, AST shape, lookup, evaluation,
or emitted CSS gets an `OPEN` row here before implementation. Its linked detail
record must state the exact owner proposal, known unknowns, and required
invariants/tests. The owner changes only the row's status/ruling when deciding;
the implementing agent then links the landed code and tests. Superseded rows
remain with their status and replacement pointer rather than being deleted.

> **C15 migration shape.** First map the current `less` package entrypoints and
> the minimal Less runtime stack they require (`less-parser`, `jess-plugin-less`,
> Less fns, resolver/config/core pieces). Prefer a thin Less-only facade if more
> than one consumer needs the assembled Less compiler; otherwise put the generic
> primitive in core and keep the Less package's glue declarative. Move `less` to
> that Less-only assembly, add a package-graph check that rejects `less -> jess`,
> and leave `jess` as the batteries-included shell that imports the first-party
> language stack. Main risks: duplicating compiler setup between `jess` and
> `less`, accidentally reintroducing a merged function registry, or making a
> facade so broad that it becomes a second product shell.

> **C16 migration shape.** Short term, dialect plugins may still seed the
> transitional evaluator slot so Less alpha can move. The target is one function
> lookup path: root capability providers are attached above the stylesheet frame,
> block-local `@plugin` functions attach to their lexical frame, and function
> evaluation asks the function family on that frame chain before deciding whether
> a call is unknown, preserved, or eligible to fall back to variable/binding
> semantics. Do not move Less/Sass registries into `jess`, do not collapse
> functions into the variable/declaration map, and do not replace this with a
> broader host object. Keep the inherited-registry path lazy: ordinary frames
> should point at the nearest parent function scope (which may itself point at a
> parent/global scope) and allocate a local function map only when a plugin
> actually registers functions in that frame.

> **C14 key-materialization limitation (2026-07-24).** `scss-parser` lowers a map
> key to a Collection entry NAME (`string | Interpolation`; `mapKeyName` rejects
> every other key with `Unsupported SCSS map key`), so the key's own value type is
> not carried on the node and `evalCollection` recovers it through the
> `materialize` sniff. Every sniff branch preserves its input bytes verbatim, so
> this cannot move output — but it is a re-classification, and a quoted key has
> already lost its quotes at parse (harmless, since Sass string equality ignores
> quoting). The `key: ValueGroup` shape is deliberately wider than what the parser
> can currently produce so that lifting the parser restriction — the real fix —
> needs no change here. Colour, list, and map keys are unreachable until then.

> **C13 implementation state (verified 2026-07-24).** `packages/fns/src/` has the
> `shared/` + `less/` + `sass/` owner split and composed `less/index.ts` /
> `sass/index.ts`. It does **not** yet have the module-granular specifiers: the
> package `exports` map is only `.`, `./builtins`, and `./package.json`, and there
> is no `imports` map — so `#less` / `#sass/color` are the target, not the current
> shape. `src/builtins.ts` still exists as the frozen parity-evidence registry
> (C6) and is not the destination.
