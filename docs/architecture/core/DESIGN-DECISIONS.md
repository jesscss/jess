# Design Decisions — canonical owner decision ledger

This is the **flat, greppable canonical ledger** for owner semantic and
architecture decisions. It holds both SETTLED rulings and OPEN owner questions,
so agents do not re-litigate settled work or silently implement an unanswered
proposal. One row per decision: the ruling/proposal + a pointer to its detail
doc and/or owner-memory note.

Rules of the road:

- **A row here is the ruling.** If code, a test, or a `.css` test-data file
  disagrees with a SETTLED row, the code/test/data is what changes — not the
  ruling. Confirm against the linked detail before acting.
- **OPEN rows are explicitly not settled** — they record the current state of a
  live thread so nobody mistakes silence for a decision.
- **"Source" pointers** are relative paths inside this dir unless prefixed
  `memory:` (a note in the owner's project memory,
  `.claude/projects/-Users-matthew-git-oss-jess/memory/<name>.md`).

## Ledger process (PROPOSED)

Every owner question that can alter parser facts, AST shape, lookup, evaluation,
or emitted CSS gets an `OPEN` row here before implementation. Its linked detail
record must state the exact owner proposal, known unknowns, and required
invariants/tests. The owner changes only the row's status/ruling when deciding;
the implementing agent then links the landed code and tests. Superseded rows
remain with their status and replacement pointer rather than being deleted.

| P13 | `.jess` has **three `$` forms, and the POSITION decides which one is legal — one form per position, no overlap**: (a) **interpolated identifiers** — selectors, property names, custom-property names, `&`-suffixes, mixin names, **at-rule preludes** — take `${…}` ONLY (`$[…]` and `$(…)` rejected); (b) **quoted strings**, `~"…"`, and `url()` bodies take `${…}` or `$(…)` (`$[…]` rejected); (c) **value positions** take `$[…]` (lookup) or `$(…)` (expression) (`${…}` rejected). Nesting like `${[$m[key]]}` is accepted as the author's problem — the spelling is committed to rather than sugared around. This REMOVED two shipped spellings: `$[…]` in identifier/string positions, and `$(…)` in at-rule preludes (`@media $(type)` → `@media ${type}`). | SETTLED (owner 2026-07-24; landed) | jess-parser `DirectJessDollarBrace` / CST `DollarBrace`; `docs/jess/02-Language/08-interpolation.mdx` |
| P14 | A **Collection is a value-keyed map, and it holds DATA only**. Its entries are a distinct `CollectionEntry { key, value }` node — **not** `Declaration` / `VariableDeclaration` — because `Declaration.name` is `string \| Interpolation`, which destroys a key's type at parse and forces it to be sniffed back from bytes (a parser-owns-structure violation). Keys are VALUES matched by value equality (`small` is the string `"small"`; `[1px]` is the number; `[red]` is the colour), following Sass, where `map.get($m, 1px)` must match the number. **Computed `[expr]:` keys are COLLECTION-ONLY** — a CSS property name is never a computed expression. **No variable declarations inside a Collection**: a binding is scope machinery, and allowing it forces every map function to decide whether `$a` is a key. The split is already there — **Collection = data, AnonymousMixin = code** — so a Less detached ruleset containing `@var: x` lowers to AnonymousMixin and the less-parser promotion heuristic must never promote a var-declaring block; the `variable` round-trip flag then dies. Lookups just take a value (`$foo[1px]`, `$foo[red]`, `$foo[$k]`) — no new syntax; this also fixes the `$m["family"]` / `$m[$k]` verbatim leak. **`foo:` and `["foo"]:` are the SAME key, stored as a PLAIN STRING, never a `Quoted` node** — symmetry with JS (`{foo: 1}` ≡ `{"foo": 1}`), and `$["foo"]` resolving differently from `$[foo]` would be unreasonable; Sass already treats `"a"` and `a` as equal map keys. Consequences: quoting becomes a SERIALIZATION decision (a stored string that is not a valid identifier, `["foo bar"]`, must be RE-QUOTED on output, so the serializer needs a bare-emittable test), and the author's original quoting does NOT round-trip (SCSS `("a": 1)` converts to `.jess` `a: 1` — a formatting change, not data loss, to be stated in the conversion notes). This makes `nth(("a": 1), 1)` → `a 1` vs dart-sass `"a" 1` INTENDED, not a quote-dropping artifact. | SETTLED (owner 2026-07-24; NOT yet implemented) | this ledger; `docs/jess/02-Language/10-namespaces-and-maps.mdx` |
| P15 | A `[…]` subscript's meaning is decided by **the subscript's own TYPE, never the receiver's**: a **number** (`$x[1]`, `$x[-1]`) is a **positional index** (negative from the end); **anything else** (`$x[small]`, `$x[$k]`, `$x[red]`, `$x["a"]`) is a **key lookup** by value equality. Receiver-type dispatch was explicitly floated and REJECTED: `$x[1]` must mean the same thing regardless of what `$x` turns out to be at runtime, so the meaning is readable from the source. Documented consequence: **numeric Collection keys are unreachable by bracket** — use `map.get($m, 1px)`. The owner accepted that trade-off; positional indexing is common, numeric keys are rare, so the rare case takes a function. No sniffing or normalisation is permitted to recover the distinction — `1` is a `Dimension` node and `"1"` a `Quoted` node, so the type is carried structurally by construction. | SETTLED (owner 2026-07-24) | this ledger; `docs/jess/02-Language/10-namespaces-and-maps.mdx` |
| P16 | **"At-rule prelude" in P13(a) means the WHOLE prelude, at every depth** — including the parenthesized and `<general-enclosed>` function bodies of an `@supports` condition. `@supports selector(${sel})` is valid; `@supports selector($(sel))`, `@supports ($(x))`, and any deeper wrapping are rejected. Wrapping never reopens a spelling: the rule is closed under `(…)`, `[…]`, and `{…}`, so `@supports foo(($(x)))` is rejected exactly like `@supports foo($(x))`. The one position change inside a prelude is a **quoted string**, which is an ordinary Jess string and therefore keeps P13(b) (`@supports selector("a $(x) b")` is valid); that string context is likewise closed under its own nesting, so a group written inside a string stays string content. Rationale: `$(…)` is a value-position EXPRESSION, not interpolation, and general-enclosed content admits literal structured bytes plus the dialect's explicit *interpolation* syntax only. | SETTLED (owner 2026-07-24; landed) | owner: "all interpolated positions just support `${}`"; jess-parser `DirectJessGeneralTemplate` (strict) vs `DirectJessGeneralQuotedTemplate` (quoted); `HANDOFF.md` general-enclosed model gate; extends P13 |
| P10 | The parenthesized parent forms split by PAYLOAD, and are not one feature: `&(X)` with a name payload is the explicit spelling of the name APPEND (`&(-1)` ≡ Less's `&-1`) and is pure selector text — landed with P9. `&('')` with an empty-string payload is AT-ROOT output placement (Sass's `@at-root`), which changes where a rule lands in the output tree; it needs an AST v2 carrier + serializer support that do not exist, and stays rejected. `&(nil)` is NOT supported: `nil` is not a Jess keyword, and whether it should become one is a separate language question. | SETTLED for `&(X)` (landed); OPEN for `&('')` (needs a carrier) | [`JESS-PARENT-SELECTOR-DESIGN.md`](./JESS-PARENT-SELECTOR-DESIGN.md) §4; `docs/jess/03-Features/02-nesting.md` |
