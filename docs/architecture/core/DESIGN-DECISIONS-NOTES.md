## J13

- 2026-10-09 — agent rationale, moved from the row (the clause is now attributed to the owner's 2026-10-09 words): The owner's 2026-07-23/24 rule is that a `&` glued to a name is Less concatenation, not CSS nesting: CSS nesting reads `.block { &__el {} }` as `&` then the type selector `__el`, and a browser drops `&-1`, so the authored form is silently dead CSS.

- 2026-10-09 — derivation (agent, 2026-10-09) from *"doesn't form a new name, so it's a plain reference to the parent, which follows CSS nesting"* and the accepted written forms (owner 2026-10-09): A `&` is a plain reference to its parent, `:is(parent)`, as in CSS nesting; it builds a name only where the text glued after it and the parent's last simple fuse into one identifier (`&__el`, `&-x`).

- 2026-10-09 — derivation (agent, 2026-10-09) from *"doesn't form a new name, so it's a plain reference to the parent, which follows CSS nesting"* and the accepted written forms (owner 2026-10-09): Under a parent of several compounds, the compound that opens the selector (nothing before it, not even a combinator) writes the parent in place, the compound's other simples joined to the parent's LAST compound with a type or universal selector leading it: `&::before` gives `P::before`, `div&` under `.a .b` gives `.a div.b` — the meaning and specificity of `.active:is(P)`, written without the one-item `:is()` around a leading parent.

- 2026-10-09 — derivation (agent, 2026-10-09) from *"doesn't form a new name, so it's a plain reference to the parent, which follows CSS nesting"* and the accepted written forms (owner 2026-10-09): Anywhere else the parent stays one unit, since `A B + A B` is not `:is(A B) + :is(A B)`: `.c &` → `.c :is(.a .b)`, `& + &` → `.a .b + :is(.a .b)`, `.c &.x` → `.c :is(.a .b).x`, `&&` → `.a .b:is(.a .b)`, `:not(.c &)` → `:not(.c :is(.a .b))`; so does a parent whose last compound names an element where the glued simple does too (`div&` under `.a span` → `div:is(.a span)`).

- 2026-10-09 — derivation (agent, 2026-10-09) from *"doesn't form a new name, so it's a plain reference to the parent, which follows CSS nesting"* and the accepted written forms (owner 2026-10-09): A name built on a parent of several compounds is placed the same way (`&__el` → `.a .b__el`, `.c &-x` → `.c :is(.a .b-x)`). A one-compound parent is written as it was where it does not open with a type or universal selector (`.x&` → `.x.a`); one that does keeps that selector first, the only simple that may lead a compound (Selectors 4 §3.1) — `.active&` under `li` → `li.active`, `.fruit-cap-&` under `apple` → `apple.fruit-cap-`, `.c .x&` → `.c li.x` — and stays one unit where the glued simples open with an element too (`div&` → `div:is(li)`) or after the compound's first `&` (`&&` → `li:is(li)`); glued text would fuse into another name (`.activeli`). Each parent of several compounds in a list a `&` distributes over follows the same rule. A parent that ends with a pseudo-element is placed by the same rule, the pseudo-element kept last, since no simple but a user-action pseudo-class may follow one (Selectors 4 §3.6.3) and `:is()` cannot hold one: `.x&` under `.a .b::before` → `.a .b.x::before` (`.x` on the element the pseudo-element belongs to, never on `.a`), `&.k` → `.a .b.k::before`, `.c .x&` → `.c .x:is(.a .b)::before`, `.x&:hover` → `.a .b.x::before:hover`; in a list `.a .b, .c::after` → `.a .b.x, .x.c::after`. Native CSS nesting gives such a `&` no meaning (CSS Nesting 1 §4: "The nesting selector cannot represent pseudo-elements"; Chrome 152 matches nothing). Escaped text a `&` references is written as it is (owner 2026-10-09: "everywhere that is text should print AS WRITTEN"): `.active&` under `@{s}` with `@s: ~".a .b"` → `.active.a .b`; a `*[…]` capture's branches are selectors and are placed (`.fruit-cap-&` under `*[apple, pear]` → `apple.fruit-cap-, pear.fruit-cap-`).

- 2026-10-09 — derivation (agent, 2026-10-09) from *"doesn't form a new name, so it's a plain reference to the parent, which follows CSS nesting"* and the accepted written forms (owner 2026-10-09): Extend composes the same selector (X5), so `.a .b { .c & {} }` is extended as `.c :is(.a .b)`; an alternative an extend splits out of a one-arm `:is()` that does not lead its selector keeps that `:is()` (`.c :is(.a .b)` + `#z:extend(.a all)` → `.c :is(#z .b)`), and one that leads is written in place (`:is(.c.k, .z) .d` + `.p .q:extend(.c all)` → `.p .q.k .d`); an `:is()` of several arms keeps J11. The default nested output writes a `&` that references its parent as authored.

- 2026-10-09 — derivation (agent, 2026-10-09) from *"&-1, &__el, &1, &-el, these all flatten / combine & and their suffix, regardless of nest flattening settings."* (owner 2026-10-09): A rule whose `&` builds a name (`&__el`, `&--mod`, `&-x`, `&-1`, `&2`, `&@{x}`, `.scss` `&` then `__el`) is written flattened in nested output, the name built. It is written where it stands: it rises out of every open rule block, inside the at-rules it is in, and those blocks are closed before it and opened again after it, so the nested output keeps the collapsed output's order and cascade (`.btn { &--primary { color: white } color: black }` → `.btn--primary { color: white; } .btn { color: black; }`); its children are written under the built name, flattened; a part of a block left empty is dropped, and when the rule writes nothing the blocks stay whole.

- 2026-10-09 — derivation (agent, 2026-10-09) from *"how do you know it's a prefix? that's why we can't do that"* (owner 2026-10-09): In `.fruit-cap-&` over an ident-led parent, `.fruit-cap-` is a complete class and the `&` is a parent reference, as in `.active&`. Only a suffix glued after a `&` builds a name.

## P46

- 2026-10-09 — the implementing lane's statement of the rule, moved from the row (agent text): A `;` in a Less mixin argument or parameter list makes every `,` in that list a comma-list comma. When a call or definition list holds any `;` separator (a trailing one included), `;` separates its arguments and every `,`, before or after the `;`, belongs to a comma-list value; with no `;`, `,` separates arguments as before. A named argument's value is the comma list of its group: `.m(@a: d, e; @b: f)` gives `@a` = `d, e`; a definition default `@m: 2, 2, 2, 2;` is one value. Storage, owner 2026-10-09: the AST holds the NORMALIZED form, the node `~( … )` builds (`Block` `paren`, `escaped`, around the `List`), so `.m(@a: d, e; @b: f)` parses to exactly what `.m(@a: ~(d, e), @b: f)` does and the separator mode never reaches the AST. Parse, owner 2026-10-09: the list is read forward once as items and separator tokens, and the reducer reassembles it when the list ends (`reassembleMixinInterior`); an item that only a `;` makes invalid raises at its own position, the first in source order, and the tolerant CST reports every one.

- 2026-10-09 — agent judgment 2026-10-09, awaiting owner (consequences the implementing lane chose): (a) in a `;` list a `@name:` may only start its comma run, and a spread or rest (`@x...`, `...`) cannot be part of a run of two or more items, though it stands alone between `;` (`.m(0; @x...)`); both are `parse/invalid-mixin-argument`; (b) a definition run that does not start with `@name:` is a pattern, so `.m(@a, @b; @c)` is a `~(@a, @b)` pattern and `@c`; (c) value-position calls (`@r: .m(…)`, `@dr(…)`, `each(.m(), …)`) read the same items as statement calls, so a spread of a non-variable value (`.m(foo...)`), never accepted in a statement call, is no longer accepted there either. `.jess` has no spelling yet for the `~( … )` node, so the `.less` → `.jess` converter names that gap for these lists.

- 2026-10-09 — resolved (agent, 2026-10-09), from *"the parens are supposed to be around a valueList"* (owner 2026-10-09): a `~( … )` argument was bound as its bytes, so a parameter holding a `;` list's comma run reached `length`/`extract`/`each` as one value (`.t(d, e, f; g)` gave `length(@a)` 1 and wrote `extract(d, e, f, 2)`) and a guard ordered two of them by their bytes. `~( … )` now binds as the `List` it holds (`mixin-dispatch.ts` `isTypedCallValue`) and reads typed as that list (`serialize.ts` `evalTypedSlot`), as a bare comma list did before P46: `length` 3, `extract` `e`, `each` iterates, and `.generic(a, b, c; a, b, d)` is not ordered, so `tests-unit/mixins-guards/mixins-guards.less` matches its golden again. An extender of several compounds that is the whole compound it stands in follows the same position rule (`.intrusion .error` + `.type1 .sidebar3:extend(.error all)` → `.intrusion :is(.type1 .sidebar3)`; a nested header appends it as `:is(.a .e)`), so nested and flattened output match the same elements: `.a .b { .x& {} }` + `.p .q:extend(.b all)` is `.a .b, .a :is(.p .q) { .x& {} }` nested and `.a .b.x, .a :is(.p .q).x` flattened (Chrome 152: both match `.q.x` under `.a` with `.p` above `.a`; the 2026-10-05 in-place header `.a .p .q` did not). The span a multi-compound target matched is the authored selector and is written back in its place. Equal-specificity members still fold into the guarded `:is()` (`.tool:extend(.btn all)` → `.active:is(.btn, .tool) .icon`). A member whose joined compound would hold two element types or two ids matches nothing and is dropped (`div.c` + `.p span:extend(.c all)` adds nothing; the match-time guard checks the member's last compound).
