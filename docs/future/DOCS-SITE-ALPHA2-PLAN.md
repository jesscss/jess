# Docs Site → "Alpha 2.0" Update Plan (Jess site, jesscss.github.io)

> **Status:** scoping only. This is a **read-only map + plan**. No page, sidebar,
> or config has been changed. The reviewed content rewrite is the follow-up.
>
> **Reference for messaging:** root `README.md` + `docs/README-POSITIONING.md` on
> `origin/dev` (the locked "What Jess unifies" convergence, honest tiering,
> ordered roadmap Less.js → Sass+ → `.jess` → minimal browser build, PostCSS-*like*,
> no premature API, perf-as-WIP). The current docs-site content predates that lock
> and violates it in several places (catalogued below).

---

## 0. TL;DR for the owner

- The **docs infrastructure is good and recent** (committed on `origin/dev`): a
  single content pool (`@jesscss/docs-content`) materialized into two audience
  "facings" (Jess → jesscss.github.io, Less → lesscss.org). It is **not** the
  problem and should be kept.
- The **content and framing are the problem.** The Jess facing still presents the
  full five-tool convergence, `.jess` native syntax, "Sass, fixed," a Tailwind
  claim, and speed claims **as shipping today** — exactly what the locked
  positioning forbids.
- **The core reconciliation:** the docs-content IA (`AUDIENCES.md`,
  `IA-PROPOSAL.md`) was designed around **three co-equal audiences with `.jess` as
  a first-class current language.** The locked positioning says the alpha's
  "today" tier is **only Less.js v5**; Sass+ / `.jess` / minimal-browser-build are
  an **ordered roadmap.** Alpha-2.0 must re-tier the Jess facing accordingly.
- **Deploy is fully manual** — there is no CI/GitHub Pages workflow. Nothing
  publishes to jesscss.github.io until the owner runs `docusaurus deploy` locally.
  So content can be staged on `dev` with zero risk of an accidental public update.

## 1. Site inventory

### 1.1 The three packages (what each is)

| Package | Role | Deploys to | Key files |
| --- | --- | --- | --- |
| `packages/docs` (`jess-docs`, v`2.0.0-alpha.1`) | **The public Jess site** | **jesscss.github.io** | `docusaurus.config.ts`, `src/pages/index.tsx`, `sidebars.js` |
| `packages/docs-less` (`@jesscss/docs-less`) | Less site (versioned 4.x + 5.x) | lesscss.org | `docusaurus.config.ts`, `versioned_docs/version-4.x/**` |
| `packages/docs-content` (`@jesscss/docs-content`) | **Canonical content pool + materializer** | — (source only) | `docs/{jess,less,shared}/**`, `scripts/build-facings.mjs`, `sidebars/{jess,less}.js`, `AUDIENCES.md`, `IA-PROPOSAL.md` |

**How the Jess site gets its content** (the important mechanic):
`packages/docs/docusaurus.config.ts` points `docs.path` at
`../docs-content/.site/jess`. That tree is **generated** by
`docs-content/scripts/build-facings.mjs` (run as a `prebuild`/`predev` hook),
which walks `docs-content/docs/**` and emits, per facing, every doc whose
`audiences:` frontmatter includes that facing. `.site/` is gitignored. So the
**Jess site = `docs/jess/**` (audience `jess`) + `docs/shared/**` (tagged with
`jess`)**, audience-gated at build time. Confirmed working: a manual
`build:facings` run materialized **42 docs → `.site/jess`**, 64 → `.site/less`.

The old `packages/docs/docs` mirror is gone; `packages/docs/sidebars.js` just
re-exports `docs-content/sidebars/jess.js`, which is a single
`{ type: 'autogenerated', dirName: '.' }` — i.e. the Jess sidebar is driven purely
by the numeric-prefixed folder structure of the jess facing.

## 2. Target IA for an Alpha-2.0 Jess site

**Design principle (the re-tier):** the Jess facing at jesscss.github.io is, for
the alpha, an **honest-alpha site whose shippable surface is Less v5** — *not* a
full `.jess`-language site. The convergence is the vision (fine to show, tiered);
Less.js is the only "today." Everything `.jess`/Sass+/API-shaped is roadmap-labelled
or deferred.

### 2.1 Ship now (Tier-1 surface)

1. **Landing** — convergence vision **with explicit tiering**: "Today: Jess *is*
   Less v5 — `.less` renders now. Roadmap: Sass+ → `.jess` → minimal browser
   build." Unmissable **alpha banner**. Approved perf line verbatim (no numbers):
   *"Speed is a core design goal. In the alpha it's still being earned — the
   architecture is built for it, the optimization work is ongoing."* First-click
   cards point at **Getting Started** and the **Less-v5 reference**, not the
   `.jess` language.
2. **Getting Started** — install (`npm install`, Node 18+ today; Jess verifies
   the current Node LTS line and the prior three LTS lines, advancing that
   minimum as the rolling window advances; pnpm only for repo dev), **CLI usage**: the distinct `jess` command, with familiar file,
   stdin/stdout, and output-path ergonomics where Jess supports them, plus
   config. `lessc` is installed only by the external `less` package; Jess does
   not claim the Less CLI compatibility contract. **No programmatic API** (`Compiler.render`
   etc.) — CLI is the public surface for the alpha per positioning.
3. **Less v5 language reference** — the v5 surface: variables (`@var`), mixins,
   **nesting preserved by default** (`--collapse-nesting` opts into 4.x
   flattening), imports / `@-import`, extend, guards, functions. Source this from
   the **shared/less pool** (tag the relevant Less-facing pages `[jess, less]` or
   use `facing_paths`) rather than re-authoring `.jess` syntax.
4. **Migrating Less 4.x → 5.x** — already exists as a shared page
   (`shared/04-guides/01-migrating-less-4-to-5.mdx`); surface it prominently.
5. **Status & Roadmap page (new, honest)** — the tiering table + the **ordered**
   roadmap (Now Less.js → Next Sass+ → Final `.jess` → After: minimal browser
   build). State the convergence capabilities as *being proven*, PostCSS-*like*
   (loose, no plugin-API spec), perf-as-WIP. This page is where the ambition lives
   without over-claiming elsewhere.

### 2.2 Defer → roadmap-labelled or omitted

- **Full `.jess` `02-Language/**` reference** — either move behind a clearly
  labelled "Roadmap / `.jess` (not yet)" section, or drop from the jess facing's
  `audiences` for now. Do **not** present as current reference.
- **Sass+ / "coming from Sass" trio** (`shared/04-guides/02-coming-from-sass/**`,
  overview's "Sass, fixed" gate) — roadmap-labelled (Sass+ = roadmap #2, not
  shipped). Keep the `sass` audience tag for the future dedicated facing, but it
  must render under a "roadmap" frame on jess, not as a current verdict.
- **Programmatic/JS-TS API docs** — omit entirely (no stabilized API in alpha).
- **`03-Features/**`** — retire (harvest nesting / CSS-in-CSS framing per
  `IA-PROPOSAL.md`).
- **Theming, minimal-browser-build, CSS-in-JS** pages — roadmap page mentions only.

### 2.3 Relationship to the existing IA proposal

`docs-content/IA-PROPOSAL.md` is a strong greenfield IA **but built pre-positioning-lock**
around `.jess` as a co-equal current language. Adopt its **mechanics** (one pool,
audience gating, shared concept + gated syntax, `03-Features` retirement) while
**overriding its tiering**: for Alpha 2.0 the jess facing leads with Less-v5-today,
not the full `.jess` language. Recommend the owner annotate `IA-PROPOSAL.md` as
"superseded on tiering by `DOCS-SITE-ALPHA2-PLAN.md` / positioning lock."

## 3. Phased rewrite plan

**Phase 0 — Owner decision (gates everything).** Confirm the re-tier: is
jesscss.github.io an **honest-alpha (Less-v5-today) site** (this plan's
recommendation, matching the positioning lock) or the **full `.jess`-language
site** (the existing IA)? Every phase below assumes the former.

**Phase 1 — De-overclaim (fast, highest impact, low risk).** Pure content edits,
no structural change:
- Rewrite `index.tsx` hero: tiering + alpha banner + approved perf line; repoint
  first-click cards.
- Rewrite `overview.mdx` + `about.mdx`: remove non-running `.jess` code blocks,
  the five/six-tool "does today" list, Tailwind, "kinda magic," speed claims,
  "Sass, fixed" as current; add the tiered "Less v5 today, rest roadmap" frame.
- Config chrome: drop **Gitter** from `docusaurus.config.ts` footer; verify
  Twitter/SO links.
- (Adjacent, flag for the README fan-out): the root `README.md` rewrite.

**Phase 2 — Re-tier the nav + add the honest status page.**
- Author the **Status & Roadmap** page.
- Move `02-Language/**` and the Sass+ trio under roadmap labels (or drop their
  `jess` audience tag) so the alpha nav shows the Less-v5 surface first.
- Wire the **Less-v5 reference** into the jess facing (tag shared/less pages
  `[jess, less]` or add `facing_paths`), so the Jess site has a real current-syntax
  reference instead of `.jess`.

**Phase 3 — Bigger lift.**
- Author/verify the full **Less v5 language + `lessc` CLI reference** against the
  *actual* alpha behavior (not the stale 4.x docs or the `.jess` pages).
- Retire `03-Features/**` (harvest first).
- **Fix every internal link** so the site builds under `onBrokenLinks: 'throw'`
  (see §3.1).

### 3.1 Does the site even build?

- **`build:facings` works** — verified (42 jess / 64 less docs materialized).
- **The Docusaurus build is a known abort risk — verify before trusting.** Two
  concrete hazards:
  1. **`packages/docs/docusaurus.config.ts` sets `onBrokenLinks: 'throw'`.** The
     jess-facing content has many hand-written cross-links (e.g. `overview.mdx` →
     `/docs/language/modules-and-imports`, `/docs/getting-started/install`,
     `/docs/guides/coming-from-sass`; `index.tsx` → `/docs/Language/overview`,
     `/docs/Functions/about`) whose **case and existence** must match generated
     routes exactly. Any mismatch **aborts the whole build**. This is the most
     likely cause of the "`pnpm -r build` docs abort."
  2. **`packages/docs-less/docusaurus.config.ts`** shells out at config-eval time
     (`npm view less versions --json`, and reads `../../../less.js/packages/less/
     package.json`). In CI / a fresh worktree with no network or no less.js
     checkout it falls back gracefully, but it's a second failure surface for a
     workspace-wide `pnpm -r build`.
- **Recommendation:** the follow-up must run `pnpm --filter jess-docs build`
  (and `@jesscss/docs-less`) to green, most likely by fixing broken links or
  temporarily relaxing `onBrokenLinks` to `'warn'` while content is in flux. Treat
  a clean `jess-docs build` as the Phase-3 exit gate. The docs sites are **private
  workspace packages**, so the abort only bites `pnpm -r build`, not the published
  npm alpha (`publish-alpha.yml` doesn't touch them).

## 4. Deploy mechanism (what triggers a public update)

**There is no CI/GitHub-Pages workflow.** `.github/workflows/` contains only
`publish-alpha.yml` (npm package publish, `workflow_dispatch`, branch `alpha`) and
`less-alpha-readiness.yml` — **neither deploys the docs site.** A repo-wide grep
for pages/gh-pages/deploy in `.github/` returns nothing.

**Publishing is manual and local**, via Docusaurus' built-in deploy:
- `packages/docs/package.json` scripts:
  - `"deploy": "docusaurus deploy"`
  - `"deploy:matthew": "GIT_USER=matthew-dean USE_SSH=true pnpm deploy"`
- `docusaurus.config.ts`: `organizationName: 'jesscss'`,
  `projectName: 'jesscss.github.io'`, `url: https://jesscss.github.io`,
  `baseUrl: '/'`.

So `docusaurus deploy` **builds the site and force-pushes it to the `gh-pages`
branch of the `jesscss/jesscss.github.io` repo**, which GitHub Pages serves at the
root domain. **The public site changes only when the owner runs
`pnpm --filter jess-docs deploy` (or `deploy:matthew`) from their machine.**

**Implication for this plan:** all Alpha-2.0 content work can land on `dev` and be
previewed locally (`pnpm --filter jess-docs dev`) with **zero risk of an
accidental public update**. The owner's manual `deploy` run is the single,
deliberate trigger — schedule it as an explicit final step once content is
reviewed and the build is green.
